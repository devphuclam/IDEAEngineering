IDEA Engineering system context

ARCH-VIEW-CTX-001 — Engineers, reviewers and scoped administrators use IDEA Engineering. Office and CAD applications are external editing tools, a company identity provider is a future option, and authorized recipients consume exact read-only Release Packages. IDEA remains the product-data authority.

IDEA Engineering candidate container view

ARCH-VIEW-CON-001 — Engineers use the Web workbench or Desktop. Administrators use the Administration Web application. All protected requests go to one IDEA Server, which owns authorization and product coordination and accesses the relational and private Artifact stores. The Workspace process alone manages local working files. Format processing is isolated from the main Server.

Candidate deployment and trust zones

ARCH-VIEW-DEP-001 — Engineer Windows PCs run browser, Desktop, Web-rendered Workbench, per-user Workspace process and external Office or CAD tools. Reviewer and administrator devices use separate Web entry points. All cross-device calls use HTTPS to a company-managed server zone containing the server, database, private Artifact store and isolated format runtime.

IDEA Server Module authority

ARCH-VIEW-MOD-001 — Scoped administrators call only their owning Modules. Identity and Accounts supplies actor eligibility, Project Governance supplies memberships, and Access Policy returns permission decisions. Controlled Product Data, Product Structure and Lifecycle Governance retain their own business authority and append committed outcomes to Audit Evidence.

Principal role Scope authorization model

ARCH-VIEW-RBAC-001 — Actors and Business Groups are security principals. Direct memberships connect Actors to Project Groups. Immutable Role Definition versions contain product Permissions, and each Role Assignment binds one principal and one role version to one Authorization Scope. Authorization decisions combine applicable assignments and retain a separate business-gate result.

Controlled Workspace publication responsibilities

ARCH-VIEW-MOD-002 — The Desktop and Workspace process call a small Controlled Product Data interface. Internal coordination validates Reservation and expected-head rules, stages candidate bytes through a storage adapter, and publishes through one authoritative database commit. A status query resolves an uncertain response by the same OperationId.

End-to-end controlled Release Spine

ARCH-VIEW-ACT-002 — A Logical Document is registered, an exact Checkout or Reference scope is confirmed, work is performed in an ordinary local Workspace, and Check-in either publishes one immutable Generation or records No Change while ending the confirmed Reservation. The exact Generation is reviewed, approved and released only after scope revalidation. Any failed Check-in preserves local work and any failed Release leaves the scope unreleased. An exact Release Package can later be reproduced and restored.

Business Revision workflow state

ARCH-VIEW-STATE-001 — A first successful Check-in moves a Revision from Start to In Work. Submit moves it to Under Review. Reject or Withdraw returns it to In Work. Approval records a decision but the Revision remains Under Review until an eligible Release succeeds. Checkout never changes this workflow.

Reservation record lifecycle

ARCH-VIEW-STATE-002 — A confirmed Checkout creates an Active Reservation. Renewal keeps that same record Active. A committed changed or No Change Check-in or governed cancel makes it Ended. Lease timeout makes it Expired. Authorized recovery makes the old record Recovered. Ended, Expired and Recovered records never become Active again; any later Checkout creates a new Reservation against the current head.

Local Reference condition and safe exits

ARCH-VIEW-STATE-003 — A Reference starts with exact local bytes for the current server head. Local editing or a newer server head can occur independently. A modified current Reference can become a working copy only after the server grants Checkout against that same Generation. A modified out-of-date Reference cannot publish directly and remains safe while the user chooses a copy, a new document, deliberate reapplication to a fresh Checkout, or confirmed discard.

Confirmed Checkout and Reference materialization

ARCH-VIEW-SEQ-001 — The engineer first sees and confirms an exact document scope. The server evaluates permission and current state for every row. One conflict refuses the requested Reservation set. If valid, the server creates Reservations only for Checkout rows, returns exact Artifact pins for both modes, and the Workspace verifies each digest before updating its manifest or opening the root file.

Modified Reference decision sequence

ARCH-VIEW-SEQ-005 — A changed local Reference cannot be checked in. The engineer may request Checkout against its exact expected Generation. Only a still-current and available Generation yields a new Reservation while keeping local bytes. Otherwise the original document is unchanged and the local candidate remains available for safe copy, current-file comparison, deliberate reapplication, Create Copy or confirmed discard.

Check-in Operation lifecycle

ARCH-VIEW-STATE-004 — The server accepts one OperationId and input fingerprint into a private resumable pre-commit state. Only complete transfer and validation reach Ready to commit, and only the authoritative database commit reaches Committed. Refused, failed and cancelled operations are grouped as ended without publication in this overview and remain distinct in the transition table. An uncertain commit outcome is held for reconciliation before the client may treat it as committed or safely resumable.

Atomic Check-in publication

ARCH-VIEW-SEQ-002 — The engineer confirms an exact scope after a complete local scan. The server fixes the OperationId input fingerprint and checks authorization, current heads and Reservations. Changed bytes are staged and digest-verified privately. At commit time the server revalidates all gates and uses one database transaction to publish every changed Generation, update heads, record any Change Set plus the operation and outbox, and end all confirmed Reservations. Any refusal or pre-commit failure publishes none and preserves local work.

Resolve an interrupted or uncertain Check-in by OperationId

ARCH-VIEW-SEQ-007 — If the commit succeeded but its response was lost, the client queries the same OperationId and receives the already committed result. If interruption occurred before commit, the server returns verified progress for safe resume. If authoritative evidence is inconsistent or temporarily unavailable, the operation is held for reconciliation and no new operation or success is inferred.

Review approval and exact Release sequence

ARCH-VIEW-SEQ-003 — An author submits one exact Generation into a Review Round pinned to workflow and approval policy versions. An eligible independent approver records a decision. Release then previews and revalidates the exact scope, structure and evidence; any blocker refuses the whole scope, while success creates one immutable Release Record without changing unrelated In Work documents.

Native account session revocation and recovery

ARCH-VIEW-SEQ-008 — Linh signs in through the IDEA client and receives a bounded session only when the account is active. Every protected resource Module asks Identity and Accounts for current eligibility before applying RBAC and its business gates. When an Account Administrator suspends the account or recovery changes credentials, affected sessions are revoked. Later requests and resumed transfers using an old session are refused, while local Workspace files remain safe. A fresh eligible sign-in keeps the same stable Actor history.

Account and Project access administration responsibility

ARCH-VIEW-ACT-001 — System Management creates and activates Linh's account without product access. A Project Administrator separately admits Linh to P-100 and its mechanical Group. Access Policy combines Group membership with a Design Engineer Role Assignment at P-100 Scope, after which the product Module still applies its business gates.

Governed Role Definition and Role Assignment lifecycle

ARCH-VIEW-STATE-005 — A Custom Role Definition candidate is edited as Draft, validated and then either refused or activated as an immutable version. Activating a successor supersedes the former definition for new selection but never changes an existing assignment. A Role Assignment is separately proposed and authorized against one exact active Role Definition version and Scope. It becomes Active immediately or Scheduled for a future effective start, then ends explicitly or expires. Replacing it requires another reviewed assignment.

Effective Permission followed by business gates

ARCH-VIEW-SEQ-004 — The authoritative resource Module resolves the current Actor and session, Project and direct Group memberships, then asks Access Policy to evaluate applicable assignments, immutable role versions, Scope, time and conditions. Even when RBAC grants the action, the owner Module revalidates current business state before committing.

Exact BOM view export and controlled import

ARCH-VIEW-SEQ-009 — The user selects an exact Structure Snapshot and BOM View Profile. Product Structure returns an authorized BOM view that pins both identities. Export creates a non-authoritative BOM Representation with source and output provenance. Import first stores a candidate and validates it against an exact base snapshot, then shows an add-change-remove preview. Only a separately confirmed, revalidated request atomically publishes a new Structure Snapshot and owning Generation; stale, invalid or unauthorized input changes nothing.

Qualified neutral Representation production

ARCH-VIEW-SEQ-010 — Format Intelligence resolves one exact source Generation, Artifact digest and versioned capability profile. For an automatic path it grants a bounded immutable-input job to an isolated format adapter, which may invoke a qualified application export or standalone converter. For a manual path it receives an uploaded candidate. Both paths verify output, source pins and producer provenance before registering a non-authoritative Representation. Failure preserves the source and records a typed result. When the source later advances, the old Representation remains reproducible but is marked Needs update for the newer head.

Resumable large Artifact transfer

ARCH-VIEW-SEQ-006 — The Workspace begins or resumes one transfer bound to an OperationId, digest and size. The server reports accepted ranges so only missing chunks are sent. Private staging verifies each chunk and the full digest; completion makes a private candidate ready but never publishes a Generation.

Artifact storage evolution boundary

ARCH-VIEW-EVO-001 — Controlled Product Data identifies Artifacts by stable identity and digest and calls one storage interface. A filesystem adapter is the current candidate; later object or multi-volume adapters can replace it. Migration copies and verifies bytes before changing location records, without changing Generations or Releases.

Coordinated exact backup and recovery

ARCH-VIEW-SEQ-011 — A backup coordinator selects one recovery point and records a recovery-set manifest that joins the database point, every required immutable Artifact, active configuration and policy versions, and required protected key material. During recovery, an operator restores these parts into an isolated replacement environment, invalidates restored sessions, reconciles later security changes, resolves every retained Generation and verifies every digest. Only an exact result with required functional checks may reopen service; any missing or mismatched item leaves recovery blocked and visible.

Protected data flow across trust zones

ARCH-VIEW-SEC-001 — Web and Desktop clients send authenticated commands to the IDEA Server over HTTPS and never receive database or permanent Artifact-store credentials. Desktop sends only allowlisted manifest-scoped commands to a per-user Workspace process over protected local IPC. Office and CAD applications edit ordinary local files and receive no IDEA authority. Server owner Modules revalidate account, RBAC and business state before using relational and Artifact stores. Format work runs in an isolated one-job zone and returns an untrusted candidate for validation. Coordinated backup copies cross into a separately controlled recovery zone and cannot reopen service without exact reconciliation.

Released baseline identity

DATA-VIEW-CORE-001 — An Operating Organization owns Logical Documents, each with Business Revisions and immutable Generations. Generation manifests identify Artifacts and may pin Structure Snapshots. A Release Record pins exact Generations, structure and approval evidence so later Working Heads cannot alter the released baseline.

Account Project and RBAC data relationships

DATA-VIEW-AUTH-001 — The Organization owns Security Principals, accounts, Projects, Role Definitions and Scopes. Actor and Business Group are mutually exclusive principal kinds. Project and Group membership are separate from Role Assignments. Each Role Assignment binds exactly one Security Principal, one immutable Role Definition version and one Scope. A decision may be supported by many applicable assignments, recorded through contribution rows. Scope parent-child rows make the hierarchy explicit without a recursive self-loop.

Artifact transfer and storage identity

DATA-VIEW-ART-001 — One Check-in Operation coordinates Artifact Transfers that assemble private staged candidates. Only a committed operation creates Generations whose manifests identify immutable Artifacts. Artifact Locations map each digest to replaceable storage providers without changing document or Generation identity.

Workspace evidence, Reservation and Check-in result

DATA-VIEW-WS-001 — A local Workspace Manifest contains entries that pin documents and expected Generations with Checkout or Reference mode and digests. The server separately owns Logical Documents, Working Heads and Reservations. One Check-in Operation contains exact entries using Reservations and expected Generations; a committed changed entry can produce one immutable Generation, while a No Change entry produces none. A successful changed operation may create one Change Set covering all produced Generations.
