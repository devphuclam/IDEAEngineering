## 1. Purpose and scope

This is a DDM-native inventory followed by a separate comparison with the current IDEA
Engineering source set. It records observable capability parity, not implementation parity. A DDM
feature is not automatically an IDEA requirement; a row marked `MISSING` can be deliberately
deferred or rejected. `COVERED` means the current IDEA documents specify an equivalent user/business
capability, not that IDEA has implemented or passed it.

The current source authority is the eight IDEA Core Product Documents and their supporting records:
DOC-04 is the normative SRS, DOC-05 the normative architecture, DOC-06/DOC-08 refine contracts,
and the Feature/Spec/Tech briefs are decision views. The briefs are read at their current pinned
versions; stale historical prose is not treated as authority. DDM public claims remain bounded by
the cited vendor material, date, release wording and demonstrated UI, as required by the product
knowledge index and ADR-0009.

## 2. Research method and limitations

1. Read the current IDEA catalogue, `CONTEXT.md`, DOC-01…DOC-08, GOV, VVP, accepted/proposed ADRs,
   current Feature/Spec/Tech briefs, brief history, change records and roadmap/dependency records.
2. Read the existing DDM baseline and bounded findings (`IE-KNW-DDM-001…006`, administration
   finding, acquisition/audit plan, and DDM comparison research) before adding claims.
3. Checked Solidmakarna/DesignDataManager first-party pages, release PDFs and official videos where
   reachable. The web tool returned empty search results and several fetch timeouts for the vendor
   site during this run; therefore the admitted repository-held first-party URLs are retained as the
   principal evidence set. No unsupported claim is upgraded because a page could not be fetched.
4. Used the public source date/version in each source row. Historical tutorial UI proves the shown
   vendor demonstration only; it does not prove a current edition, entitlement, backend schema,
   enforcement, transaction, security, recovery or performance result.
5. Compared each individual capability to exact IDEA FTR/REQ/other sources. `SPEC-OPEN-02…08`
   remain open; DDM evidence contributes questions and bounded evidence but cannot close IDEA policy.

This document is not a target-package audit, interoperability test, security assessment, benchmark,
implementation report or parity certification. The target audit remains gated by `IE-VVP-DDM-001`.

## 3. Evidence and comparison rules

### 3.1 DDM evidence classes

| Class | Meaning in this matrix |
|---|---|
| `CONFIRMED-OFFICIAL` | Capability directly documented by Solidmakarna/DesignDataManager in a page, release note, data sheet or course outline. |
| `CONFIRMED-OBSERVED` | Capability visibly demonstrated in a credible official video/UI; the observation does not prove backend implementation. |
| `SUPPORTED-SECONDARY` | Credible partner/reseller material supports the behavior but direct official confirmation is absent. |
| `INFERRED` | A bounded inference from observed behavior; never presented as a DDM fact. |
| `UNKNOWN` | Evidence is insufficient, contradictory or target-specific evidence is unavailable. |

### 3.2 IDEA coverage and relevance

Coverage is exactly one of `COVERED`, `PARTIAL`, `MISSING`, `DEFERRED`, `OUT-OF-SCOPE`,
`NOT-APPLICABLE` or `UNKNOWN`. Relevance is independently one of `CORE-V0-CANDIDATE`,
`POST-CORE-CANDIDATE`, `OPTIONAL`, `DO-NOT-COPY` or `RESEARCH-REQUIRED`.

`P0` means a potential PG4/correctness blocker for the intended Golden Path; `P1` is an important
product gap; `P2` is later parity/usability; `P3` is optional/niche; `N/A` is not a gap. A
`PARTIAL` or `MISSING` row must carry `P0`–`P3`. For `DEFERRED`, `OUT-OF-SCOPE` and `UNKNOWN`
rows, `P0`–`P3` may record candidate priority but is not a defect severity; use `N/A` where no
priority is useful. None of those states is silently treated as a defect.

## 10. IDEA deliberate improvements / stronger semantics

The following are already supported by current IDEA sources and are intentionally not weakened for
surface parity. They are product invariants, not claims about DDM internals.

| IDEA invariant | What current IDEA specifies | What DDM evidence establishes | Why IDEA should retain it |
|---|---|---|---|
| Immutable Generation identity | `REQ-ID-002`, DOC-05/06 and `ADR-0005` distinguish Business Revision, Version and immutable Generation; changed Check-in creates exactly one Generation and No Change creates none. | DDM shows Issue/File Version and historical loading, but not immutable generation keys or save cardinality (`VER-001…004`). | Exact history and conflict validation require an unambiguous snapshot; surface terminology cannot justify weakening it. |
| Exact release pinning | `REQ-STR-001…005` and `REQ-LC-008` pin Structure Snapshot, BOM profile, representations, documents and Artifacts. | DDM demonstrates selective/staged release but does not prove exact membership, digest or historical reconstruction (`REL-001…005`). | A controlled release must be reproducible after later child revisions. |
| Representation source pinning and freshness | `REQ-FMT-005` records source Generation/digest/tool, `Current` versus `Needs update`, and policy-selected Release blocking. | DDM demonstrates PDF/neutral generation/regeneration but not source pin, digest, stale state or release gate (`CAD-007`, `PREV-005`). | Derived files must not silently masquerade as the current source. |
| Server-authoritative ActorContext | IAM establishes the Actor from session proof; the owner requests authorization; Access Policy resolves current IAM/Project evidence. Client-supplied `ActorId` is never trusted. | DDM admin UI shows users/groups and access cells, but not trust establishment or lower-path enforcement (`SEC-001…007`). | Prevents identity spoofing and keeps authorization explainable across Web/Desktop/Workspace. |
| Authorization Decision versus Owner Command Outcome | `DOC-05/06`, `REQ-AUTH-006…010` and VVP-007 separate eligibility from lifecycle/Reservation/completeness outcome; owner evidence and Audit/outbox commit atomically. | DDM permission summary shows a granting group, but no comparable separation or transaction contract is public (`SEC-004`, `AUD-003`). | A granted permission must not be mistaken for a successful business command. |

isolation, evidence, stop and exit criteria.
